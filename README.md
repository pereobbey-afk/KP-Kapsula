# ИИ Сметчик — Капсула

Внутренний инструмент компании «Капсула» для расчёта стоимости ремонтных работ
по загруженной проектной документации.

Сотрудник загружает дизайн-проект, частичный проект или только план помещения,
отвечает на несколько общих вопросов и нажимает «Рассчитать смету». Система сама
определяет тип документа, извлекает объёмы, проверяет полноту и формирует смету
по действующему прайс-листу.

## Состояние

Приложение работает локально и в Docker. Настоящие прайсы разобраны и
импортированы, настоящий проект проходит весь путь до сметы и экспорта.

Не закрыто:

- **ключ ИИ API** — не задан; конвейер проверен на заглушке Anthropic API
  через настоящий SDK, но не на живой модели, поэтому качество распознавания
  чертежей не измерено;
- **публикация** — адрес развёртывания не определён, production e2e не выполнен.

Подробности — в разделе «Что осталось» ниже.

## Особенности прайса «Капсулы»

Файлы прайса — это шаблоны сметного расчёта (Приложение №1 к Договору),
а не простые прайс-листы. Из их фактической структуры следуют правила:

- колонка **«тип»** отделяет работы от материалов; материалы в каталог не
  попадают вовсе — модель не должна их видеть;
- работа названа **«позиция»**, единица — «ед. изм.», цена — «Стоимость»
  (соседняя колонка «Объем» ценой не является);
- строки **«Второй этап:»** и **«Итого за второй этап:»** — маркеры, а не
  разделы; иначе работы получили бы неверную принадлежность;
- один раздел содержит **блоки по поверхностям без заголовков**: стены м²,
  стены м/п, потолок м², потолок м/п. Общие работы («Грунтовка»,
  «Обеспыливание») повторяются с разной ценой, а различает блоки только
  строка-якорь вида «Шпаклевка стен» / «Шпаклевка потолка», идущая следом.
  Поэтому поверхность входит в признак позиции;
- **10 позиций** имеют одинаковое описание, но разную цену, и различить их
  по файлу невозможно. Обе расценки сохраняются и помечаются: строка сметы
  по такой позиции получает уточнение о необходимости проверки. Список — в
  отчёте импорта (`--dry-run`), их стоит поправить в исходном файле.

## Архитектура

Ключевое решение: **расчёт не привязан к HTTP-запросу**.

```
браузер ──► web (Fastify)          worker (отдельный процесс)
             │  создаёт задачу         │  забирает задачу из очереди
             │  отдаёт jobId           │  classifying → extracting →
             │  отдаёт статус          │  validating → calculating
             ▼                         ▼
           SQLite (WAL) ◄──── общая durable-очередь ────┘
```

- Веб-сервер только создаёт задачи и отдаёт статус. Он ничего не считает.
- Анализ идёт в отдельном процессе. Его длительность ничем не ограничена
  со стороны веб-слоя.
- Состояние задачи живёт в БД, а не в памяти процесса или вкладки браузера.
- Воркер держит задачу в аренде и продлевает её heartbeat. Если воркер умер,
  аренда истекает и задачу подбирает другой воркер — проверено убийством
  процесса через `SIGKILL` на середине анализа.
- Сессия интерфейса не участвует в жизненном цикле задачи: расчёт переживает
  её истечение.

Почему не serverless: требование «анализ вне жизненного цикла запроса» и запрет
имитировать фон таймером внутри функции исключают эту модель. Нужен
долгоживущий процесс.

## Запуск

### Локально

```bash
npm install
cp .env.example .env          # заполните SESSION_SECRET и ANTHROPIC_API_KEY
npm run migrate               # создать базу
npm run build

npm start                     # веб-сервер на :3000
npm run start:worker          # воркер, в отдельном терминале
```

В разработке удобнее три процесса: `npm run dev`, `npm run dev:worker`,
`npm run dev:web` (интерфейс на :5173 с проксированием `/api`).

Первая регистрация в интерфейсе создаёт администратора. Дальше учётные записи
заводит он.

### Docker

```bash
export PUBLIC_URL=https://адрес-развёртывания
export SESSION_SECRET=$(openssl rand -hex 32)
export ANTHROPIC_API_KEY=...        # только в окружении, не в репозитории

docker compose up -d --build
```

Оба процесса используют один образ и делят тома `data` (база) и `storage`
(загруженные файлы). Воркеров можно запустить несколько — аренда задач не даст
им взять одну задачу дважды.

## Прайс-лист

Единственный источник расценок — активная версия прайса. Импорт:

```bash
npm run pricelist:import -- \
  --file "./prices/price_01.07.2026.xlsx:01.07.2026:2026-07-01" \
  --file "./prices/price_05.08.2026.xlsx:05.08.2026:2026-08-05" \
  --label "Объединённый прайс Капсула" \
  --dry-run
```

Порядок файлов значения не имеет: приоритет редакции определяется датой.
При совпадении позиции более свежая редакция вытесняет старую, уникальные
позиции старых редакций сохраняются.

`--dry-run` показывает отчёт без записи: сколько работ и разделов получилось,
что вытеснено, что не принято и почему. Сверьте отчёт с исходными файлами,
затем повторите без `--dry-run` и с `--activate`.

Поддерживаются `.xlsx` и `.csv`. Колонки определяются по заголовку; если
раскладка нестандартная, задайте её явно:
`--col-name 1 --col-unit 2 --col-price 3 [--col-section 0] [--col-code 4]`
(нумерация с нуля).

Ни одна строка исходного файла не исчезает молча: у каждой непринятой в отчёте
указана причина и место в файле.

## Правила расчёта

- `стоимость строки = объём × цена позиции активного прайса`;
- целевой цены за м² не существует; цена за м² — производный показатель
  `итог / площадь`;
- материалы не считаются; стоимость дверей, сантехнических приборов,
  светильников, кухни, мебели и техники не входит;
- деньги считает код в целых копейках через BigInt, а не модель;
- цена приходит только из БД: заявка на объём поля цены не имеет, поэтому
  подменить её запросом невозможно;
- перед сохранением и экспортом смета заново сверяется с прайсом;
- ручная правка помечается и теряет статус «подтверждено проектом»;
- неизвестные объёмы не попадают в итог — они показываются отдельно.

## Роль ИИ и безопасность

Модель извлекает и структурирует факты. Она не считает деньги и **не видит цен**:
ей выдаётся каталог работ с кодами и единицами, а в ответе она возвращает код
и объём. Цену подставляет сервер из БД, несуществующий код отбрасывается.

Отсюда следует главное свойство: даже полностью подчинившийся инъекции ответ
модели не способен изменить денежный итог. Максимум — исказить объём, и это
видно в источнике каждой строки.

Защита от prompt injection двухслойная: содержимое документов объявлено
недоверенными данными в инструкции, а структурный барьер описан выше.
Если модель замечает в документе попытку управления, пользователь видит
предупреждение в смете.

Прочее: секреты только в окружении; файлы проверяются по расширению, MIME,
сигнатуре и размеру; PDF под паролем отклоняется; ответ модели валидируется
строгой схемой; чужую задачу или смету перебором идентификатора не получить;
в логи не пишутся секреты и содержимое документов.

   документа, обновление страницы во время расчёта, открытие сметы, экспорт.
